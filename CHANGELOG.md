# V3.1.0
- Labels can now be given in **several languages**. The languages belong to the project rather than to the individual node: the globe button at the left of the toolbar switches the display language for the whole canvas, and *Manage languages…* in its menu defines which languages the project has. One of them is the **primary** language — the one written without a suffix, and the one everything falls back to. Instance labels and Explorer names are multilingual; the ID column is not, because an instance has one identity however many names it is given.
- On a node, the two label rows gain a small language strip at their right edge. It says two things at once: which language the row is currently showing (outlined) and which languages already hold a value (solid) rather than none (faded) — so missing translations are visible across the whole canvas without opening anything. Clicking a language switches that one row; the toolbar button switches every node at once. Typing and dragging a column both land in whichever language the row is showing, so a table with `SE_Bez` and `SE_Bez_en` needs no new gesture, just the row switched over. With a single language nothing of this renders and the node looks exactly as it did.
- **A long-standing export bug is fixed along the way.** Until now the RDF export wrote every `rdfs:label` as `"…"@en`, hard-coded in three places, whatever language the text was actually in — a German dataset was therefore labelled English throughout. Labels now carry the language they were written in. Opening a project saved before this version says so, and writes its labels in the project's primary language instead; if that language is wrong for a particular project, the language button changes it. The backend keeps `@en` for a caller that sends no language at all, so a replayed TSV or an external script produces exactly what it always produced.
- Changing the primary language moves the existing text with it rather than relabelling it. The plain node fields *are* the primary language, so switching from German to English without moving anything would leave German text in the field the exporter then tags `@en` — the very mistake above. Removing a language is spelled out before it happens, with the number of nodes whose labels it would delete.
- **Verify** now reports missing translations: one line per additional language, with the number of nodes and the first few names. That is deliberately where the bulk question is answered — it is what lets the indicator on the node stay as small as it is.
- Every export carries the languages. RDF writes one `rdfs:label` per language with the correct tag; the TSV gains four `@tag` columns per additional language, appended after all existing ones; the Graph Explorer JSON gains `l_i18n` per node, `typeLabelsI18n` / `edgeLabelsI18n` in the schema block, and a top-level `languages`. GraphML stays single-language — it is a picture for yEd, not a round trip. The Explorer does not read the new fields yet and shows the primary language; since all of them are additive, nothing breaks in the meantime.
- Project files are written as **version 6**: one new `languages` block, and three `*I18n` maps on the nodes that only appear where a second language is actually used. Older files load unchanged, and a single-language project writes byte-identical TSV, RDF and Graph Explorer JSON to version 3.0.0 — verified against the full test dataset (38,787 triples, 3,481 nodes).
- **The application now runs fully offline after setup.** The IBM Plex fonts used to be fetched from Google Fonts on every start, which meant a request to an external service — including the visitor's IP address — despite the promise that nothing leaves the machine. They now ship with the application (`frontend/public/fonts/`, SIL Open Font License, licence file included), and the frontend makes no external request at all.
- **An ontology that cannot be read is now reported.** Until now such a file was skipped silently: it simply did not appear in the list, and only the class and property counters hinted that something was missing. Loading now names every file that could not be parsed, and confirms a successful load with the number of classes and properties found. A backend that cannot be reached is reported as well, instead of ending up in the browser console only.
- The field **Inverse Explorer-Name (Property)** in the connection dialog now says what it actually does. Its placeholder and help text asked for the URI of an inverse property, while the export has always used whatever is entered as the name of the opposite direction in the Graph Explorer — a plain name works, a property URI makes the export take that property's label. The help text now says so, and warns that only the text after a `/` or `#` is shown.
- The user interface is English throughout. A few German leftovers are gone — the subclass marker in the Triple Explorer and its triple preview, the PNG and SVG entries of the Export menu, the Verify message for unconnected nodes, and the error message for an RDF export that produced no triples. Table placeholders and the table dropdown now say "1 row" instead of "1 rows".
- `setup.bat` now ends with a *Setup complete!* message and waits for a key press, like `setup.sh`. Previously its window closed the moment setup had finished, which was easy to mistake for a crash.
- The example project in `0_exampleData/` is now a version 6 file with English and German labels, and its RDF, TSV and Graph Explorer exports have been regenerated from it, so all files in the folder describe the same state.
- The **README** has been rewritten as a complete user guide: a short overview for experienced users, then twelve chapters in working order — from loading ontologies to saving projects — with new screenshots and animations of the current interface, plus example data, CIDOC CRM support and troubleshooting.
- The backend now reports version 3.1.0 as well; it still said 3.0.0.

# V3.0.0
- The **RDF Pipeline** has been removed. It was a three-step workflow that pushed the exported TSVs through a locally running Ontotext Refine instance into a GraphDB repository — useful when it was the only way out of the application, but the direct RDF export has covered the same ground for some time, in six formats and without any external service. Gone with it: the toolbar button and its wizard, the six backend endpoints (`/pipeline/ontorefine`, `/pipeline/ontorefine-literals`, `/pipeline/graphdb/repos`, `/pipeline/graphdb/create-repo`, `/pipeline/graphdb/repo/{id}`, `/pipeline/graphdb/import`), the `requests` dependency that served them, and the bundled `ontorefine-cli-1.2.1` JAR. The application no longer needs a Java runtime, and the repository is 12.7 MB lighter.
- Step ① of that pipeline survives as **TSV (URI + Literal)** in the Export menu: it downloads `Triples_URI.tsv` and `Triples_URI_literal.tsv`, the two intermediate tables with fully resolved URIs that the RDF and Graph Explorer exports are built from. They are produced by the same exporter as before and follow the same rule as every other written file — the rows of the tables currently loaded in the panel. Anyone running their own Ontotext Refine setup can keep feeding it these files by hand.
- The three export buttons now carry the three brand hues instead of two: **Export** turquoise, **RDF** pink as before, **Explore** yellow — the shade the removed RDF Pipeline button used to occupy. Each fill comes from the `--brand-*` palette with the one-shade-darker edge of the same hue, and the label colour follows the contrast rather than the other way round: dark ink on turquoise (6.3:1) and yellow (8.6:1), white on pink (4.6:1), all of them above the AA threshold.
- The source tree was tidied for the release: `GraphCanvas.jsx` (never imported — the canvas lives in `App.jsx`) and two `.bak-vor-tabellen-restore` backups are gone, as are `pandas` and `openpyxl`, which sat in `requirements.txt` without ever being imported. Every file under `frontend/src/` is now actually bundled and every listed package actually used. The example project ships as a v5 file that names its three tables, so they bind to their placeholders by file name on load.
- Nothing else changed. Project files, the RDF export in all six formats, the Graph Explorer JSON, GraphML, PNG and SVG are byte-for-byte what they were; `/pipeline/rdf-export` and `/pipeline/graph-explorer-json` keep their paths, historic prefix and all. Only a caller that addressed one of the six removed endpoints directly will notice, and will get a `404`.

# V2.1.0
- Loading a project no longer re-creates its tables. The rows a project file carries are the state of the data when it was saved, and a project is usually re-opened in order to feed it *updated* tables — so the table panel now shows one empty placeholder per table the canvas refers to, naming the nodes and the mapped columns that are waiting for it. Loading a file into a placeholder hands it that table's id, so every column mapping on the canvas stays valid and the new rows reach the nodes at once; a file loaded under a name the project already knows binds itself. For the case where the stored rows *are* what is wanted, the placeholder offers them with one click. Importing RDF or a non-project JSON still builds its tables from the data, unchanged.
- Every file written from the canvas now uses the tables as they are loaded at that moment. The project file, the Graph Explorer JSON and the RDF export took their rows from the snapshot each node was mapped with, so a table corrected outside the application only reached an export after re-dragging its columns. Updating a dataset — added, changed or deleted records — is now a matter of loading the table again and exporting; tables that are not loaded fall back to the rows stored in the project and are named in a note, so it is always visible which part of an export is not current. The graph verification reads the same current rows.
- A table can be re-loaded from its own tab (↻ Reload) whatever the new file is called. The previous route — an upload matching the old file name — still works, but a renamed or re-exported file used to arrive as a second, unconnected table.
- A file loaded through the panel finds its own placeholder. The file name decides where a project written by this version or later knows the answer already; for everything else the columns do, because the same table exports the same header set however many rows were added or deleted in between, and a file that gained or lost a column still counts as long as every mapped column is there. A match only binds when exactly one placeholder fits — two placeholders with the same columns (an old table and its newer version, typically) stay untouched rather than guess.
- A placeholder says what it is waiting for, which matters for the projects that carry no table names at all: the nodes that read from it with their ID and label columns, the number of stored rows and columns, and the first rows as they stand in the project file. Recognising "the find inventory" or "the stratigraphy" from that takes a glance.
- A placeholder can also be pointed at a table that is already loaded. A table replaced by a newer version under a different name leaves its id on every node mapped before the swap, so a project can refer to more tables than were ever loaded; the dropdown moves those nodes over to the loaded table in one step, reporting any column the new table no longer has.
- Project files are written as version 5: they gain a `tables` section holding the name, columns and row count of every table used, and the nodes now remember which file their rows came from — saving stamps the name of every currently loaded table onto its nodes, so it survives into the next session. Older project files load unchanged; their placeholders carry the table id as a name, because that is all those files know.

# V2.0.0
- Loading a project now refills the table panel. The rows were always in the file — every exporter reads them straight off the node — but the panel stayed empty, so their columns could not be dragged and no *further* node could be mapped without uploading the source file again. The tables are reconstructed from the nodes and handed to the panel through the same path the graph import already uses, so they behave exactly like uploaded ones. This works for every project file; no format change was needed. Tables that carry no name (saved before this change) show their table id.
- The nodes hanging off a node can now be folded away with the ⊟ button in its header; the button shows how many nodes are currently hidden and brings them all back. A node is only hidden when the collapsed node is its sole owner, so deep chains fold away completely while a node that another parent also points at stays visible. The button only appears on nodes that actually own children exclusively. Hiding is display only: hidden nodes remain in the project file and in every export unchanged.
- Nodes can now be collapsed to their class name, either individually via the arrow in the node header or for the whole canvas via **Collapse** in the toolbar. Collapsing only hides — every mapping, label and connection stays in place, the state is saved with the project, and no export is affected. Small icons on a collapsed node show whether an Explorer name, a label and an ID column are set.
- The canvas can now be zoomed out much further (down to 2 % instead of 50 %). A large imported graph spans several thousand pixels, and "fit view" was previously clamped to the old floor — which showed a fragment of the layout and made a perfectly ordered graph look unsorted.
- Dot-One qualifier nodes of an imported graph are now placed next to the connection they annotate instead of a whole column further right, so the dot-one edge no longer cuts back across the diagram.
- Imported graphs are now arranged as a layered layout instead of a grid, so connections run left to right and the graph is readable without rearranging it by hand.
- RDF-star is now read on import. Files using quoted triples (`<<S P O>> …`) previously failed to parse entirely; their annotations now come back as Dot-One qualifiers on the connection, so stratigraphic above/below relations survive the import.
- TriG and N-Quads files are now read completely. Statements inside named graphs were previously dropped, which reduced an 18 MB file to a handful of connections. Graph membership itself is not restored; the import reports how many named graphs were merged.
- Existing graphs can now be imported: **Import** reads RDF (Turtle, TriG, N-Triples, N-Quads, RDF/XML, N3, JSON-LD) as well as a Graph Explorer JSON. All instances sharing an `rdf:type` become **one** node, with the instances kept in a table behind it — a graph with 4,000 instances therefore arrives as roughly a dozen nodes. Its classes can then be replaced with CIDOC CRM classes and its connections re-drawn like any other node. The import produces ordinary mapped nodes, so it uses the same export path as everything else; a round trip over a real graph returned all 6,349 connections and all 3,352 attributes unchanged.
- Removing a value in the edge editor now takes effect: a join key that had once been assigned could not be removed again — the previously stored key was silently restored on save. The same applies to the Dot-One fields.
- Explorer names and node labels can now be removed with a dedicated button on the node and in the edge editor. Previously the only way was to empty the input and click away, which relied on the field losing focus; if that did not happen, the field looked empty while the old name was still stored and exported. Values are also stored trimmed now, so a name consisting only of spaces counts as removed.
- The class of a node can now be changed after the fact (e.g. `E18_Physical_Thing` → `E22_Human-Made_Object`) via the replace button in the node header. Only the class itself is replaced: all connections, column mappings, labels, Explorer names and the literal setting are kept, so the project file as well as the GraphML, JSON and RDF export simply carry the new class where they carried the old one. The dialog reports beforehand which outgoing connections the ontology does not define for the new class; those connections are nevertheless kept unchanged.
- The application has been renamed from **Table2Knowledge Studio** to **OntoCartographer Studio**. Existing project files continue to load unchanged; only the name and the documentation are affected.
- Custom Explorer names can now be assigned to nodes and connections. Such a name replaces the ontology class or property name in the GraphExplorer view, and connections sharing the same Explorer name are merged into a single group there. Explorer names are used exclusively in the JSON export and leave the RDF export unchanged.
- A JSON export for the GraphExplorer has been added. Free-text values that had to be modelled as separate nodes on the canvas (e.g. a note attached via `P3_has_note`) are folded into the attributes of their parent node instead of being exported as standalone nodes. The GraphExplorer itself is not published yet.
- The inverse of a connection can now be controlled manually: an inverse property URI can be entered where the loaded ontology declares no `owl:inverseOf` or where a custom property is used, and the creation of the inverse relation can be switched off per connection.
- Both inverse controls are now disabled for connections whose range is a free-text value (`rdfs:Literal`, `xsd:*`, `geo:wktLiteral`), with a note explaining why. Such values are folded into the attributes of their parent node and never become nodes of their own, so there is no opposite direction to name — previously an inverse name could be entered there and was then silently dropped on export. Existing values are kept in the project file, but remain without effect.

# V1.1.0
- Key handling has been improved: instead of a single join key, it is now possible to select separate join keys for domain (source) and range (target), ensuring correct cross-table joins.
- A new widening function has been added: it is now possible to separately activate or deactivate widening for parent properties (properties inherited from parent entities) and child properties (properties defined on child entities).
